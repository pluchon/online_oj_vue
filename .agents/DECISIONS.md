# DECISIONS

> 项目进行中定下的决策。**只追加，不改历史**——决策被推翻时新写一条，在旧条目标注「已被 D-00X 取代」。
> 这是为了让后来的 agent 知道「为什么是现在这样」，而不是重新推一遍、或者改回被否掉的方案。

## 格式

### D-00X · YYYY-MM-DD · 一句话标题

- **决策**：选了什么
- **否决了**：考虑过哪些别的方案
- **理由**：为什么
- **影响**：哪些任务 / 模块要跟着变
- **决策者**：用户 / `agent名`

### D-001 · 2026-09-24 · 下一阶段只补 OJ 的基础功能

- **决策**：做题目标签、题解、提交管理与重判、数据概览四块；AI 只再加一个功能（赛后复盘或弱项推荐二选一）。
- **否决了**：多语言判题、讨论区 / 评论、Rating 积分与全站排行榜、题单、题目批量导入导出。
- **理由**：用户希望项目不做复杂，但基础功能要齐全。AI 模块已经覆盖出题、帮建竞赛、辅导、语义检索、相似题和资料审核，缺的是传统 OJ 的基础功能。多语言判题要为每题维护多套 main 函数，出题和 AI 生成用例都要跟着改；讨论区要连带做审核、通知和举报，投入产出比都低。
- **影响**：PLAN.md 的 M1–M5。
- **决策者**：`claude-code` 提议，用户同意落档

### D-002 · 2026-09-24 · 标签由出题人维护，取代关键词推断

- **决策**：新建标签表和题目标签关联表，标签在 B 端维护；friend 删除 `resolveQuestionTags` 的关键词推断，能力雷达图改用真实标签统计。
- **否决了**：继续扩充关键词规则；让 AI 在查询时实时推断标签。
- **理由**：关键词推断出题人改不了，也不准；雷达图、相似题、AI 帮建竞赛的检索和后续的弱项推荐都需要准确的标签。AI 只在出题时建议标签，由出题人确认后保存。
- **影响**：T-001 ~ T-005，以及 T-015 中的弱项推荐。
- **决策者**：`claude-code` 提议，用户同意落档

### D-003 · 2026-09-25 · 新表主键用雪花 ID

- **决策**：标签表、题目标签关联表、题解表的主键都用雪花 ID。
- **否决了**：像 `tb_question_case` 那样用自增主键。
- **理由**：项目主键有意使用雪花 ID；题目表本身就是雪花 ID，关联表要存题目的雪花 ID，两边保持一致。
- **影响**：T-001、T-006。
- **决策者**：用户

### D-004 · 2026-09-25 · 标签功能不新增路由页面

- **决策**：M1 的标签功能全部放在现有页面里：B 端题目管理页用弹窗管理标签，题目抽屉里选标签，列表加一列；C 端题库筛选栏加标签和做题状态筛选，题目卡片和做题页显示标签。
- **否决了**：B 端单独做一个「标签管理」侧边栏页面。
- **理由**：标签只是题目的一个属性，数量不多，弹窗就够用；不新增页面也省去单独设计 UI。新控件照搬现有的难度分段和 `OjDialog` 样式。
- **影响**：T-002、T-004。
- **决策者**：用户

### D-005 · 2026-09-25 · 标签带分类，能力雷达图按分类统计

- **决策**：`tb_tag` 增加 `category` 字段（1 数据结构、2 算法、3 数学、4 其他）；雷达图中数据结构、算法、数学三个维度，按通过的题所带标签的分类计数。
- **否决了**：维护一份写死的「标签 → 维度」映射；雷达图继续用关键词匹配。
- **理由**：关键词匹配改不了、也不准；分类由出题人在建标签时选定，新增标签不用改代码。分类也用于下拉框分组。
- **影响**：T-001、T-003；B 端标签管理弹窗需要选择分类。
- **决策者**：`claude-code`（实现 M1 时补充，用户未单独确认）

### D-006 · 2026-09-25 · 标签名唯一约束用生成列

- **决策**：`tb_tag` 使用虚拟生成列 `active_name = IF(delete_state = 0, tag_name, NULL)` 并建唯一索引，Service 层也会先查重。
- **否决了**：直接给 `tag_name` 建唯一索引（逻辑删除后同名标签无法重建）；删除时改名。
- **理由**：只约束未删除的标签，删掉的标签不占用名称；实体类不映射这一列。
- **影响**：T-001。
- **决策者**：`claude-code`

### D-007 · 2026-09-25 · C 端标签放在标题后，竞赛中隐藏

- **决策**：题库卡片把标签放在标题后面，不放在中间区；做题页在竞赛答题模式下不显示标签。
- **否决了**：放在中间区攻克状态后面（中间区的几列是等宽对齐的，标签长短不一会把这几列挤乱）。
- **理由**：保持中间区对齐；标签会提示解法，竞赛中不宜展示。
- **影响**：T-004（相应调整了 D-004 中「题目卡片中间区」的描述）。
- **决策者**：`claude-code`

### D-008 · 2026-09-25 · 题解独立成表，按是否通过决定查看方式

- **决策**：新建题解表，一道题一篇，主键雪花 ID，逻辑删除。已通过的学员直接看；未通过或未登录时点开页签先确认再看；竞赛答题中不显示页签，friend 带进行中竞赛的 examId 请求时拒绝返回。
- **否决了**：在题目表上加字段存题解（题目表越来越宽，以后加作者、更新时间都得改题目表）；未通过时完全不让看（学员卡住时没有出路）。
- **理由**：题解和题目生命周期不同；确认框既保留独立思考的提示，又不把人卡死。
- **影响**：T-006 ~ T-009。
- **决策者**：用户（按 `claude-code` 的建议）

### D-009 · 2026-09-25 · 竞赛中题解按「题目是否在进行中的竞赛里」拦截，题解随题目保存

- **决策**：friend 查询题解时，只要题目属于任一场已发布且在比赛时间内的竞赛就拒绝（错误码 3305），不依赖前端是否带 examId；B 端题解放在题目抽屉里，随「保存提交」一起保存，不单独提供题解保存接口。代码里题解统一叫 `editorial`，与已有的 AI 解法示例 `solution` 区分。
- **否决了**：只在带进行中竞赛 examId 时拒绝（D-008 原文）——参赛者从题库入口直接打开同一道题就能绕过；题解单独保存接口——抽屉里会出现两个保存动作，新建题目时还没有题目 ID。
- **理由**：防作弊要在后端兜住；一个保存动作更不容易漏存。代价是比赛期间非参赛者也暂时看不到这道题的题解。
- **影响**：T-006、T-008、T-009；网关白名单新增 `/friend/question/*/editorial`（免登录查看）。
- **决策者**：`claude-code`（实现 M2 时细化 D-008）


### D-010 · 2026-09-26 · C 端题库筛选收成一行下拉，标签用级联

- **决策**：题库筛选只保留一行：左侧搜索，右侧三个胶囊下拉——难度、标签（第一级分类，第二级「全部某分类」与各标签）、做题状态（仅登录）；选了非「全部」的下拉用墨绿描边高亮。
- **否决了**：两行布局（用户觉得不好看）；难度与状态继续用分段按钮（一行放不下）；标签用「分类 + 标签」两个下拉（多占一个位置，B 端仍保留两段式）。
- **理由**：一行更紧凑；级联一个控件就能表达「只选分类」和「选具体标签」两种筛选。
- **影响**：C 端 `QuestionList`；替代 D-004 里 C 端「难度分段旁加标签下拉和做题状态分段」的做法。
- **决策者**：用户提出方向，`claude-code` 定具体形式

### D-011 · 2026-09-26 · compose 密码用变量引用、保留本地默认值

- **决策**：Redis、RabbitMQ 的密码在 compose 里写成 `${OJ_REDIS_PASSWORD:-123456}`、`${OJ_RABBITMQ_PASSWORD:-123456}`，与各服务 Nacos 配置读取的变量同名；健康检查从容器环境变量取密码。
- **否决了**：完全去掉默认值、强制在 `.env` 里填（各服务的 Nacos 配置模板里也带同样的本地默认值，只改 compose 一边会让两边不一致；强制改密码会让服务起不来）。
- **理由**：与仓库里 MySQL 的现有写法一致，一个变量同时配置容器和服务；部署时在 `.env` 和服务环境变量里设同一个值即可覆盖。T-017 验收标准写的「仓库里搜不到明文 Redis 密码」没有完全做到：本地默认值仍在，只是不再写死。
- **影响**：T-017、`deploy/.env.example`。
- **决策者**：`claude-code`

### D-013 · 2026-09-26 · 题目分为刷题题与竞赛题

- **决策**：题目表加 `purpose`（1 刷题，默认；2 竞赛），一道题只属于一种。C 端题库（列表、统计、上一题 / 下一题、相似题、搜索推荐）只出刷题题；竞赛题只能从竞赛进入（题目详情要带已开赛竞赛的 examId）。竞赛选题（手动与 AI 帮建）只能选竞赛题。竞赛题不提供题解与 AI 辅导。用途只能从竞赛改为刷题，且题目所在竞赛都结束后才能改；刷题题编辑时用途不可选。存量数据：被尚未结束的竞赛使用的题标为竞赛题，其余为刷题题。
- **否决了**：按「题目是否在进行中的竞赛里」临时判断（D-009、T-016 的做法，未开赛的竞赛题仍会在题库里提前曝光）；允许刷题改为竞赛（题目已被人做过、题解已公开）。
- **理由**：从源头把竞赛题和刷题题分开，题解、AI 辅导、题库曝光都按用途判断，规则简单。竞赛结束后由管理员把题目改为刷题，题目才进入题库。
- **影响**：T-021；D-009 与 T-016 的进行中竞赛判断保留作兜底。
- **决策者**：用户（按 `claude-code` 的建议，并补充了切换规则）


### D-014 · 2026-09-26 · 竞赛结束即公开：题解解锁、不再复用、定时转为刷题

- **决策**：
  1. 竞赛题所在的竞赛全部结束后，题解与 AI 辅导解锁（赛后练习可用）；同一道题可同时在多场未结束的竞赛里，等最后一场结束才解锁。
  2. 已在结束的竞赛中公开过的题不能再加入新竞赛（3216），选题弹窗里标「已公开」且不可勾选。
  3. XXL-JOB 新任务「公开已结束竞赛的题目」（`questionPublishHandler`，每 5 分钟第 30 秒）调用 oj-system，把所在竞赛全部结束的竞赛题改为刷题，题目随后进入 C 端题库。
- **否决了**：允许复用已公开的题并重新锁定题解（学员已看过题目与题解，新竞赛不公平，还会出现正在看题解突然被锁的情况）；把公开步骤挂在排名结算任务里（题目归 oj-system，结算在 oj-friend，失败应互不影响）。
- **理由**：题目一旦在竞赛结束后公开就不再保密，规则放在选题一步即可根除冲突；公开的自动化复用现有调度中心，不引入新组件。
- **影响**：T-021；取代 D-013 中「竞赛题一律不提供题解与 AI 辅导」「竞赛结束后由管理员手动改为刷题」两点（管理员仍可手动改）。
- **决策者**：用户（按 `claude-code` 的建议）

### D-015 · 2026-09-26 · 按题重判的范围

- **决策**：重判某道题时，重判它的练习提交和未结算竞赛（进行中、已结束但未结算）里的提交；已结算竞赛里的提交不动。确认框先展示会重判多少条、涉及哪几场竞赛、跳过多少条已结算的提交。重判期间提交记录回到「评测中」，重复点击只投递还没在评测中的记录。
- **否决了**：连已结算竞赛一起重判并重新结算（排名和战报已发给参赛者，事后改名次会引起混乱）；只重判练习提交（未结算竞赛到结算时还会用错误结论算分）。
- **理由**：练习提交的结论直接影响做题状态和通过率，必须能纠正；未结算竞赛在结算时按新结论计分即可，已公布的结果保持不变。
- **影响**：T-011、T-012。
- **决策者**：用户（按 `claude-code` 的建议）
